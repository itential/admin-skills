# Contributing

Pull requests into `main` must pass the checks below (see `.github/workflows/pr-compliance.yml`).

## Branch names

`<type>/<description>` — type is one of `feature`, `fix`, `refactor`, `docs`, `chore`; description is lowercase letters, numbers and hyphens. Example: `feature/add-gateway-admin`.

The branch prefix also sets the PR label (and so the version bump in release notes): `feature/` → `feature`, `fix/` → `fix`, `refactor/` → `refactor`, `docs/` and `chore/` → excluded from the changelog.

## Commit messages

Conventional commits: `<type>[(scope)]: <description>` with type `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore` or `perf`. No merge commits — squash or rebase.

## What to edit

- Skill content: `skills/<name>/SKILL.md`. Keep each skill self-contained — any file it references lives inside its own folder, referenced by a relative path (**Skills Valid** checks this). If a skill has an `assets/` folder, it's generated by `scripts/check-generated.sh` — commit its output.
- Never add files under `skills/*/custom/` here — that folder is for customers' own copies (**Custom folders empty** fails otherwise).
- Don't change versions in a normal PR. Releases are cut by a maintainer — see **Releasing** below.

Before pushing, run `scripts/check-generated.sh` — the same check CI runs.

## Releasing

Versions are bumped by hand, in their own PR, when a release is wanted:

```bash
git checkout -b chore/release-0-2-0
python3 scripts/bump_version.py --bump minor      # or patch / major — updates every manifest
git commit -am "chore: release v0.2.0"
```

After it merges, publish the draft release on GitHub with the matching tag (`v0.2.0`). **Manifest Versions** fails any PR where the manifests disagree.
